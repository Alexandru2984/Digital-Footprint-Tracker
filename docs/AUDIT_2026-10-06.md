# Full audit — 2026-10-06

Security, performance, and dead/duplicate code, each from scratch over the
whole repository: 26k lines of Swift in 188 files, 9k of frontend, 5k of
scripts, 1.4k of ops configuration and the 3k-line Python worker. The earlier
code audit (`SECURITY_AUDIT_2026-08-30_CODE.md`) was not used as a guide; it
was consulted only at the end, so nothing already fixed is reported as new.

**O8, done differently.** Persisting risk score and count would have needed a
migration, a backfill and a write path to keep them true. Batch-loading one
page's results in a single query removes the N+1 at today's sizes with none of
that.

**O3, kept on purpose.** Re-verifying the whole ledger every five minutes is
what catches an edited *old* `audit_logs` row; an incremental check from the
last verified head would only look at new rows and would lose that. The cost is
negligible (13 ledger events in six weeks), and the 250,000 cliff is not silent:
it reports `verification_limit_exceeded` as a critical log line and in metrics.

**O4, partly.** `investigation.js` and `dark-web.js` (about 25 KB compressed)
still load with the page. They wire their own buttons when loaded, so loading
them later means giving each an entry point; they already sit at the end of the
body and do not block rendering.

### Found while fixing

- **Reports and holehe were broken in production.** `fpdf` was not installed,
  so every PDF report failed with 500, and the holehe binary was missing, so the
  email plugin found nothing. Fixed with a hash-locked Python runtime built in
  place under `/opt/swift-vapor-python` (`10e23df`), checked by preflight. The
  report generator also moved off fpdf2's deprecated `ln=` argument.
- **Session writes before a throw are lost.** Vapor's `SessionsMiddleware`
  saves the session only on a successful response, so `session.destroy()`
  followed by `throw` did nothing: the pending 2FA login survived the error
  meant to end it. Replaced by deleting from the session driver directly
  (`SessionSecurity.invalidate`), and the per-login 2FA attempt counter lives
  in memory for the same reason (`f9933d9`).
- **Two worker dependencies gained advisories** during the work (mako,
  multidict); bumped with verified hashes (`ffd4df6`).
- **Shares had the same 403/404 split as S2**, in two more handlers; fixed with
  it.
- **The installed preflight lagged the repository.** A deploy updates the
  release, not `/usr/local/libexec/swift-vapor`; the drift check caught it and
  the installed copy was refreshed.

Not addressed: the smaller duplicates listed at the end of the dead-code
section (worker configuration parsing, the Identity/Timeline scan prelude, the
executive summary prose). Each is small and stable; merging them would cost
more review than it saves.

## Security

### Method

The attack surface was derived from code, not documentation: every route and
its middleware from each controller's `boot`, then every handler classified by
how it obtains a user and whether it filters by owner, with the ambiguous ones
read by hand. Then each sink class: outbound HTTP, subprocesses, raw SQL, HTML
and XML generation, DOM writes, redirects, cryptography, logging, error bodies.
Ops and the Python worker were read directly. For a second opinion independent
of the repository's own semgrep rules, semgrep's public `security-audit`,
`secrets`, `javascript`, `python`, `nginx` and `dockerfile` rulesets were run
over 318 files. gitleaks scanned all 324 commits.

### S1 — Medium: no per-account throttling on password or TOTP

`AuthRateLimiter` keys on client IP only, in memory, at 10 attempts per 5
minutes; there is no per-account failure counter anywhere. An attacker with
many addresses scales linearly against a single account. At the TOTP step the
window is ±1 step — three valid codes in 10⁶ per guess — and a wrong code does
not end the pending login, so guessing continues until its 300 s TTL.

Everything else in 2FA is sound: replay protection under a row lock, atomic
recovery-code consumption, session rotation at both login stages.

**Fix:** a per-account failure budget across all IPs with progressive delay,
returning the same generic error; end the pending 2FA session after a handful
of wrong codes. Avoid hard lockout, which turns into a denial of service
against the victim.

### S6 — Medium (functional): the Tor mirror cannot log in

`CSRFMiddleware` accepts only the configured `ALLOWED_ORIGIN`. Tor Browser
sends `Origin: http://<onion>`, so every POST through the onion vhost fails:

```
onion    POST /api/auth/login  →  403 {"reason":"Cross-origin request blocked."}
clearnet POST /api/auth/login  →  401 {"reason":"Invalid username or password."}
```

The onion vhost deliberately disables only `register` and
`resend-verification`, so login was meant to work there. The proxy does not
rewrite `Origin` — CSRF protection is intact; the allowlist is simply
incomplete.

**Fix:** allow the onion origin explicitly. Tor Browser treats `.onion` as a
secure context, so the `__Host-`/`Secure` session cookie works there.

### S4 — Low: field encryption writes the v1 envelope

`TokenEncryption` v2 derives a per-field key with HKDF and binds key ID, field
and row UUID as AAD, so a ciphertext moved to another row or column fails to
decrypt. Production runs `ENCRYPTION_WRITE_VERSION=1`, which has no AAD. No
encrypted column holds plaintext; today the gap covers one value, a v1 TOTP
secret.

**Fix:** switch the write version to 2 and rewrap with the existing
`SensitiveFieldRewrapper`.

### S5 — Low: the notification test endpoint is unthrottled

`POST /auth/notifications/test` needs a session but has no rate limit, so an
account can drive unlimited outbound HTTPS POSTs to any public URL it sets as
its webhook. Delivery itself is well defended (HTTPS only, DNS-pinned, redirect
hops re-validated, path redacted in logs); only the volume is unbounded.

### Informational

- **S2** — `NotificationController.markRead` and `APIKeyController.delete`
  return 403 for another user's object and 404 for a missing one, unlike every
  other handler. With 122-bit random UUIDs this cannot be exploited.
- **S3** — `holehe`, `whois` and the VoidAccess worker receive the target as a
  positional argument without `--`. Every entry point rejects a leading hyphen,
  so this is not exploitable, but the invariant is not preserved downstream:
  `TargetDeriver` can produce `-foo` from `.-foo@x` or `_foo` (those reach only
  HTTP plugins), and the worker's `TARGET_RE` permits a leading hyphen.
- **S7** — `scans.user_id` is `ON DELETE SET NULL`. Account deletion deletes
  scans explicitly, so nothing leaks today, but any other deletion path would
  turn private scans into capability-readable ones (`ScanAccess`).
- **S8** — the port-80 redirect is `https://$host$request_uri`; a fixed host is
  tighter.
- **Known, owner action** — `.env.bak-mailcow-20260816T221809Z` still holds
  plaintext secrets in the working tree.

### Verified clean

- **Authorization** — all ~80 handlers. Every non-public one obtains the user
  and filters by owner, mostly with 404 for foreign objects. API keys are
  deny-by-default: an unclassified route refuses them.
- **Sessions** — `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Strict`,
  absolute TTL, database-backed, rotated at login and at the 2FA step.
- **CSRF** — normalized `Origin`/`Referer` against the configured origin,
  `Sec-Fetch-Site: cross-site` refused, missing provenance refused for
  authenticated sessions, API-key requests correctly exempt.
- **SSRF** — numeric IPv4 forms (decimal, hex, octal, short), IPv6 on an
  allowlist (2000::/3 only, IPv4-mapped refused, NAT64 re-checked), fail-closed
  DNS that blocks on *any* internal answer, and connections pinned to the
  validated IP at every redirect hop. All outbound HTTP goes through it; the
  only other client talks to a configured worker URL with UUID-built paths.
- **SQL** — 123 raw statements, every interpolation a `bind:`; no
  `unsafeRaw`, no string concatenation.
- **Subprocesses** — no shell, isolated environment, timeouts, output caps;
  user data reaches Python via stdin; `curl` gets `--disable` first.
- **Output encoding** — the HTML report escapes every interpolation; GraphML
  escapes and drops XML-illegal control characters, with generated node IDs.
- **Frontend** — 53 `innerHTML` writes reviewed: all escaped, numeric, or
  fixed. Every redirect targets `/`. CSP has no `unsafe-inline`.
- **Cryptography** — bcrypt cost 12 with the 72-byte limit enforced, 192-bit
  share tokens stored hashed, CSPRNG throughout, HKDF-separated blind indexes.
- **Worker** — HMAC with clock-skew window, `compare_digest`, replay cache.
- **Headers** — HSTS with preload, CSP with a per-request nonce, `nosniff`,
  `X-Frame-Options: DENY`, verified live through Cloudflare on every path.
- **Errors and logs** — no error object in a response, no secret in a log line.
- **Secrets** — gitleaks: no leaks in 324 commits.

### Alarms raised and withdrawn

Recorded because an audit that hides its own mistakes cannot be believed on the
rest.

- **"Argument injection into holehe."** `EmailAddress.normalize` allows a
  leading `-`, but `InputValidator` rejects it, and *every* entry point —
  including pivot targets extracted from third-party pages — goes through it.
  Downgraded to S3.
- **"Production serves no CSP or HSTS."** The grep pattern required `:`
  directly after `strict-transport`, so it could never match
  `Strict-Transport-Security:`. A correct pattern showed all six headers
  present. Lesson: an absence result means nothing without a positive control.
- **"Emails stored in plaintext."** `User.email` is plaintext by design — it is
  needed for login, uniqueness and delivery. It is not an encrypted field.
- **"Account deletion leaves scans ownerless."** The FK is `SET NULL`, but the
  handler deletes scans and shares explicitly first. Kept only as S7.

## Performance

Production volume is small — 12 users, 9 scans averaging 6.0 s (max 20.4 s),
about 6 results per scan — so most of this is about growth. Postgres
statistics were read from the live database.

### O1 — Nine foreign keys without a supporting index

`results.scan_id` is the hot one: every results view, export and diff filters
on it, and `results` has only its primary key. Also `scans.user_id`,
`investigations.user_id`, `scheduled_scans.user_id`, `tags.user_id`,
`api_keys.user_id`, `scan_tags.tag_id`, `export_jobs.scan_id`,
`notification_outbox_events.scan_id`.

Postgres does not index foreign keys automatically, which also makes
`ON DELETE CASCADE` scan the whole child table for each deleted parent:
retention cleanup removing many old scans becomes quadratic.

### O8 — "My scans" is N+1

`UserController.myScans` and `adminScans` load **every result row** of each
listed scan, one query per scan, to count them and compute a risk score; with
O1 each query is a full scan of `results`. Persisting risk score and result
count when a scan completes turns the list into one query.

### O2 — Idle polling

`NotificationDeliveryWorker` and `ExportJobWorker` poll every 2 s
(`*_POLL_SECONDS=2`): 5.56 million index scans recorded against an empty
`notification_delivery_jobs`. An in-process wake-up when a job is enqueued,
with a 30 s fallback poll, cuts idle queries roughly fifteenfold and lowers
pickup latency.

### O4 — JavaScript a scan never needs

A first visit downloads `d3.min.js` (92 KB compressed), `qrcode.js` (12 KB,
2FA setup only), `investigation.js` (19 KB) and `dark-web.js` (6 KB). Loading
them when their feature opens cuts first-visit JavaScript by about two thirds.

### O5 — Inline JavaScript in uncacheable HTML

64% of `index.html` (170 KB, ~35 KB compressed) is one inline script. The
per-request CSP nonce makes the HTML uncacheable (`cf-cache-status: DYNAMIC`),
so every page view downloads it again. As an external file versioned by
content hash, as `tailwind.css` already is, it would cache and leave the CSP
with fewer hashes.

### O9, O3, and what was left alone

- **O9** — `CorrelationController` loads every completed scan with all results
  per request, unbounded per user.
- **O3** — `AuditIntegrityMonitor` verifies the full chain every 5 minutes,
  loading all of `audit_logs` (24,901 sequential scans for 85 rows), and
  `AuditIntegrityLedger` throws `verification_limit_exceeded` past 250,000
  events. Not a concern at today's rate; incremental verification from the
  last verified head would remove both the cost and the cliff.
- **Left alone:** `OutboundHTTP` creates an `HTTPClient` per request. That is
  the price of per-request DNS pinning, and the main workload
  (`BulkUsernamePlugin`) reaches mostly distinct hosts, so pooling would gain
  little. Each deploy also compiles Swift on the VPS (~20 min); a deliberate
  trust choice, noted rather than changed.

## Dead and duplicate code

### Method and its limits

Swift: every function and type declared under `Sources/` was matched against
real references — calls, member access, `use:` handlers — across `Sources/` and
`Tests/`, after which each candidate was checked by hand. This found seven
false positives that are called only inside string interpolations, and two
genuinely dead symbols. Name-based matching cannot see a dead method that
shares its name with a live one, or dead enum cases and properties; Periphery
would, but ships for macOS only.

Registration was checked directly: all 33 plugins are registered and all 41
migrations are added. No script or frontend file is referenced by nothing. The
SQLite driver and XCTVapor are test-only dependencies, correctly.

Duplicates: jscpd (token-based, 70-token minimum) over Swift, the application
JavaScript including the inline block extracted from `index.html`, the scripts
and the worker. **0.93% duplication** — 234 lines in 22 clones, all Swift; zero
in JavaScript, Bash and Python.

### Findings

- **D1** — `struct GeoQuery` (`HealthController.swift:31`) and
  `func envelopeVersion` (`TokenEncryption.swift:174`) are unreferenced.
- **D2** — `myScans` and `adminScans` share ~49 duplicated lines across four
  clones, including the O8 loop. One helper fixes both.
- **D3** — `SSRFGuard.resolvesToInternal` and `resolveValidatedIP` each walk
  `getaddrinfo` results. In security-critical code a fix applied to one copy
  and not the other is the realistic failure; one resolver returning the
  address list, with both derived from it, removes it.
- **D4** — three HTML escapers (`escapeHtml` twice, `esc` in `admin.js`). The
  admin one does not escape `'`; all five of its uses are element content, so
  nothing is exploitable, but they should agree.
- Smaller: worker configuration parsing duplicated between
  `ExportJobConfiguration` and `NotificationDeliveryConfiguration` (31 lines);
  the same scan-loading prelude in Identity and Timeline controllers; the
  summary prose produced twice by `ExecutiveReport` and `ExecutiveReportHTML`.
