# Asynchronous export operations

The asynchronous export path moves potentially expensive scan serialization and
PDF generation out of request handlers. It is owner-scoped, database-backed,
bounded, cancellable, and safe to run in more than one application process.

The original capability-based synchronous routes remain available for backwards
compatibility. Durable jobs intentionally require an authenticated owner; an
anonymous scan ID is not enough to create a persistent server-side artifact.

## API contract

- `POST /export-jobs` accepts an owned terminal `scanID` and one of `json`,
  `graphml`, `markdown`, `html`, or `pdf`.
- `GET /export-jobs` and `GET /export-jobs/:id` expose only the caller's bounded
  job metadata.
- `GET /export-jobs/:id/manifest` returns completeness, result-set digest,
  artifact digest, size, format, source status, and generation timestamps.
- `GET /export-jobs/:id/download` decrypts and authenticates the artifact,
  verifies its byte count and SHA-256 again, and returns it as an attachment.
- `POST /export-jobs/:id/cancel` immediately terminates pending work or marks a
  running job for cooperative cancellation. A cancelled job cannot publish an
  artifact because completion is compare-and-set on `cancel_requested = false`.

Browser calls require a recent interactive session. Stateless API keys require
the `scans:read` scope. Every job lookup includes both job ID and caller user ID;
cross-owner probes receive the same 404 as an unknown ID.

## State and concurrency

```text
pending -> processing -> completed
                    |-> failed
          |------------> cancelled
```

PostgreSQL claims use `FOR UPDATE SKIP LOCKED`. Each claim records a random
worker ID and a bounded lease. Progress heartbeats extend the lease. Completion,
failure, and cancellation update only a row that is still `processing` and
still owned by that worker. If a worker dies, another process may reclaim the
expired lease up to `EXPORT_MAX_ATTEMPTS`; an old process cannot overwrite the
new owner. Expired final leases become `failed` with the non-sensitive code
`worker_interrupted`.

PostgreSQL check constraints reject unknown formats/states, invalid progress or
attempt counts, leases on non-processing rows, artifacts on non-completed rows,
and missing or misplaced failure codes. These constraints contain corruption if
an application regression bypasses the normal state-transition code.

All failure codes are fixed machine values. Exceptions, scan inputs, filesystem
paths, generated bytes, ciphertext, and provider/subprocess output are never
written to job error fields or logs.

## Resource limits

Defaults:

| Variable | Default | Accepted |
|---|---:|---:|
| `EXPORT_WORKER_ENABLED` | `true` | explicit boolean |
| `EXPORT_POLL_SECONDS` | `2` | 1–60 |
| `EXPORT_LEASE_SECONDS` | `120` | 60–600 |
| `EXPORT_RETENTION_HOURS` | `24` | 1–168 |
| `EXPORT_MAX_OUTSTANDING_PER_USER` | `3` | 1–20 |
| `EXPORT_MAX_JOBS_PER_USER_PER_DAY` | `20` | 1–200 |
| `EXPORT_MAX_RESULTS` | `10000` | 1–50000 |
| `EXPORT_BATCH_SIZE` | `250` | 25–1000 |
| `EXPORT_MAX_SOURCE_MIB` | `10` | 1–16 |
| `EXPORT_MAX_ARTIFACT_MIB` | `20` | 1–32 |
| `EXPORT_MAX_ATTEMPTS` | `2` | 1–3 |

Invalid present values fail application boot. Job creation locks the PostgreSQL
user row before checking outstanding and daily quotas, so concurrent requests
cannot race past the limits. Results are read in stable UUID pages; result count,
decoded source bytes, generated bytes, PDF stdin/stdout, subprocess time, and
retry count all have independent ceilings.

All export-job HTTP routes additionally share a per-process rate limit of 30
requests per authenticated user per minute (five per unauthenticated client IP).
The database-backed creation quotas remain authoritative across replicas.

PDF generation uses the fixed local Python interpreter and bundled script with
an allowlisted environment, private temporary directory, discarded stderr,
30-second deadline, bounded stdout, and cancellation-triggered process
termination. No shell is involved.

## Encryption, integrity, and retention

Artifact bytes are base64-wrapped and encrypted as `export_jobs.artifact`.
The small manifest is independently encrypted as `export_jobs.manifest`. Both
use the record UUID as authenticated context and participate in resumable key
rotation. Filenames derived from scan targets therefore exist only inside the
encrypted manifest.

Completed artifacts receive a fresh expiry window. Failed and cancelled jobs
retain only metadata and are deleted on the same bounded retention sweep.
Deletion of either the user or source scan cascades to its jobs. Account GDPR
exports include job activity metadata but do not duplicate generated artifacts.

The current storage backend is PostgreSQL, which keeps backup/restore and key
rotation atomic with the source rows. Object storage is a future scaling step;
it must preserve per-object encryption, integrity manifests, expiry, and owner
authorization rather than exposing bucket URLs directly.

## Metrics and alerts

`/metrics` publishes queue depth, processing count, failed rows, expired leases,
oldest pending age, and terminal counters. Prometheus rules alert on a five-minute
queue delay, unrecovered lease, and repeated failures. These signals are rollout
requirements, not proof that paging is currently active in production.

Repository verification covers owner isolation, API-key scope denial, artifact
encryption and digest verification, bounded source failure, cancellation,
subprocess cancellation, stale-worker compare-and-set, and key rewrapping. A
disposable PostgreSQL 16 migration check also verifies all four queue indexes,
both cascade foreign keys, and ten simultaneous `SKIP LOCKED` claims producing
ten distinct leases.

## Deployment and rollback

1. Back up and restore-test the database.
2. Deploy code that understands the new table and encrypted-field identifiers.
3. Run the explicit migration unit with `EXPORT_WORKER_ENABLED=false`.
4. Start the accepted web/worker release and verify queue metrics at zero.
5. Create one small JSON export, verify manifest and digest, then cancel one
   queued fixture and confirm it never produces an artifact.
6. Exercise PDF only after the exact Python runtime passes its smoke test.

Rollback must first stop new job creation and let active leases finish or be
cancelled. Old binaries do not know the new encrypted fields and must not run a
key rotation that omits them. The table may remain in place during binary
rollback; dropping it destroys retained downloads and requires explicit operator
approval.
